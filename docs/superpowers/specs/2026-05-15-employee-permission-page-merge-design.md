# 员工维护与用户权限合并设计

## 背景

客户档案和用户边界已经明确：系统只有内部用户和外部用户。外部用户在客户履约运营台管理，内部用户由后台管理。当前内部用户仍分散在“员工维护”和“用户权限”两个页面，系统菜单也保留两个配置项，Van 要求合并为一个员工维护页面，配置项也合并。

## 产品目标

- 系统菜单只保留“员工维护”一个内部用户入口。
- 员工维护页同时维护内部员工资料、登录启停、密码设置/重置和内部角色。
- 用户权限不再作为独立页面、独立菜单项或默认视图配置项出现。
- 旧链接 `view=userPermissions` 兼容跳到员工维护，避免历史收藏或旧操作路径直接掉到默认页面。
- 外部用户继续只在客户履约运营台维护，不进入员工维护角色配置。

## 设计方案

### 前端入口

`CompanyStaffView.vue` 保留部门模式和员工模式。员工模式合并原 `UserPermissionsView.vue` 的账号与角色能力：

- 新增员工区保持姓名、电话、部门、启用状态。
- 员工列表行内保留资料编辑。
- 同一行增加账号列：可登录/已停用、设置密码/重置密码。
- 同一行增加内部权限列：勾选内部角色并保存。
- 角色列表过滤 `customer_` 前缀，避免外部客户业务角色回流。
- 员工列表继续调用 `/api/company/employees`，账号列表调用 `/api/auth/internal-accounts`。

### 菜单与配置项

- `menu-ia.js` 的系统组移除 `userPermissions`，只保留 `departments`、`employees`、`audit`。
- `App.vue` 不再导入或直接渲染 `UserPermissionsView.vue`。
- `view=userPermissions` 通过别名归一化为 `employees`，打开旧链接时显示员工维护。
- `authz.defaultViewPermissions()` 移除 `userPermissions`，只保留 `employees` 作为内部用户管理视图配置项。

### 后端与权限边界

不新增后端接口。员工资料 API 继续由公司员工模块处理；登录启停、密码、角色 API 继续由 auth 模块处理，并保留后端权限校验。页面整合不降低 API 权限边界。

## 测试策略

- 前端/源码守护：员工维护页必须包含账号、密码和内部角色能力；用户权限独立视图不再被 App 直接引用。
- 菜单测试：主菜单不包含 `userPermissions`，旧键不再是主配置项。
- AuthZ 测试：默认视图权限不再包含 `userPermissions`，`employees` 仍可解析。
- 既有 API 测试继续覆盖 `/api/auth/internal-accounts` 只返回内部用户。

## 操作手册

更新设置审计手册、需求说明和验收用例：

- 管理员进入“系统 / 员工维护”完成员工资料、账号和角色维护。
- 不再提示进入“用户权限”页。
- 外部用户仍进入客户履约运营台维护。
