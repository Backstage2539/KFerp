# PR-525 按备注和收件地址重新提炼客户类型验收记录

## 范围
- 继续使用 PR-523 的 Excel 只读副本和稳定来源键，只重新生成客户导入审核候选。
- 备注为空时按收件人形成零售客户；备注非空时按备注客户主体聚合，并按规范收件地址数量推断批发或渠道客户。
- 本需求不执行正式客户导入，不修改正式客户、商品、订单和订单明细。

## RED / GREEN
- RED：新增备注客户/零售收件人隔离、单地址批发、多地址渠道、ERP 正式类型保留和审核导出字段测试后，旧实现缺少客户类型证据字段和审核工作簿列，测试失败。
- 数据质量 RED：首轮真实数据渲染发现包装、不贴、标签、发货和库存操作说明被误识别为客户；补充真实样例测试后收紧解析规则，并修复 `【收件人】` 标签残留。
- GREEN：`go test ./internal/migration/orderliststaging ./cmd/orderlist-staging ./internal/interfaces/http/support -count=1` 通过；备注客户、零售收件人、地址类型、关系称谓审核和 CSV/工作簿字段合同均有测试覆盖。

## 数据与工作簿证据
- 2,109 条原始业务行和 2,104 条有效订单候选保持不变；重新提炼出 1,121 条客户导入审核候选，其中零售 604、批发 451、渠道 66。
- 559 条为 `auto_ready`，562 条为 `needs_review`；334 条无法安全提取备注客户名称，207 条缺少主手机号，51 条保留多个历史手机号，均留在审核证据中。
- 66 条渠道候选均至少包含 2 个规范收件地址；不存在零售候选带非空备注、渠道候选少于 2 个地址或批发候选多于 1 个地址的规则冲突。3 条备注客户未解析到地址，已明确标记待审核。
- `客户导入审核` 保留 KFerp 客户 API 全字段，并增加推断客户类型、判定依据、收件人、规范收件地址数、地址样本、最新备注和历史备注。
- 工作簿保持 12 个工作表；artifact_tool 完成汇总、客户 API 字段区、类型证据区 inspect，公式错误扫描为 0，并完成全部工作表渲染检查。

## 隔离证据
- 源 Excel、生产客户只读快照、CSV/JSON 和审核工作簿继续保存在 git 外受保护目录。
- 本流程不对正式 `nocodb` 执行客户 INSERT、UPDATE 或 DELETE；完成后通过生产 PostgreSQL 只读查询复核正式客户数量仍为 6。

## 结论
- 客户类型审核表已按备注、收件人和规范地址证据重新生成，正式客户表零写入。所有候选仍须人工审核后才能进入后续正式导入流程。
