# PR-543 销售规格件数档位与发布名称规范化验收

## 范围

- 新 `quantity_basis=sales_spec_count` 阶梯在平铺价格行、预览、新发布、公开页和 PDF 中只显示件数，例如 `2-13件`。
- 商品名和销售规格保持分离；服务端对新草稿和新发布执行同一名称规范化，无客户别名时使用父商品名，有真实客户别名时保留别名。
- 历史发布及其 PDF、订单和财务快照不迁移、不回写；本轮只部署开发环境，不自动重新发布现有价格表。

## TDD 与实现证据

- RED：`node --test src/lib/costing-price-list-workflow.test.js src/lib/costing-bean-list-version-ui.test.js` 为新增件数 helper 缺失和页面仍使用规格拼接函数失败（61/63 通过）；最初的服务端测试因规范化函数缺失而编译失败；独立复核发现旧客户端价格行仍可污染发布名称，真实 HTTP → Service 测试随后稳定复现服务端仍保存旧 `2-13个227g` 标签；support contract 因 PR-543 种子缺失失败。
- GREEN：相关前端 6 个测试文件首次合跑 208/208，服务端加固后再跑相关 6 文件 125/125；Costing application、PostgreSQL repository、真实 HTTP API 和 support 包通过；`go test ./... -count=1` 全量通过；Vite 生产构建完成 401 modules；`scripts/verify_kferp.sh changed` 与 `git diff --check` 通过。
- PDF：服务端真实渲染 `/tmp/pr543-pdf-qa/pr543-piece-tier.pdf`（1 页）并检查 PNG；两张“白月光瑰夏”卡片分别独立显示 `规格：227g / 454g`、`2-13件 / 14件+` 以及各自单价单位，标题未拼规格。
- 服务端边界：父商品名来自当前商品档案查询，不信任客户端名称快照；价格行、分组档位和预览 `prices` 会同步按 `min_qty/max_qty` 冻结为件数标签；嵌套 JSON 字符串请求也会回填规范后的结构。
- 名称边界：无客户别名使用父商品档案名；明确客户别名优先于旧通用显示快照；两者都不追加 `227g`、`454g` 等规格。
- 展示边界：阶梯显示 `1件`、`2-13件`、`14件+`；规格通过独立 `sales_spec / 规格` 属性展示；单价继续使用具体 SKU 的 `元/227g`、`元/454g` 等单位。
