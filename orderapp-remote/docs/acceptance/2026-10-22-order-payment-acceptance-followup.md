## 根因与修复

1. **冻结与实收保护依赖客户端协议。** 原网页在运费锁定时省略运费协议，而服务端只在重新报价时检查锁定；付款保护也只在本次生成运费快照时执行。省略协议即可把已收100元的应收改为99元。这与现有手册“减费造成超收须先走财务核对”冲突，不能视作允许的多收款。
   - `repository.go` 在整单编辑事务内独立检查实际运费锁定；已有运费快照的订单即使请求省略协议也执行实收保护。
   - 与既有携带协议的请求保持同一整单冻结规则。网页显示冻结原因并停止保存，明确指向员工小程序的独立付款与发货状态入口。
   - 独立状态端点仍可在已确认实际运费后登记付款，保留商品与运费快照。
2. **成功保存后未回读。** 普通订单内嵌表单保留保存前的 `edit_revision`、运费 token、付款状态与预付款，下一次提交产生版本冲突，界面字段也落后于详情。
   - 成功后通过共享 API 客户端重新读取编辑数据，刷新全部付款字段、凭证及两个版本后才结束保存。
   - 不复用保存前正在进行的 GET；卸载/新加载后不应用过期结果。回读失败时明确说明写入已经成功，阻止旧表单重复提交，并要求关闭后重开。
   - 保存拒绝时保留输入，不触发成功事件或重新加载。
3. **普通零单价夹具不合法。** 上轮直接把普通订单商品单价和总额写成0，不符合既有价格规则。没有修改价格验证。
   - 普通订单合法零应收使用正数价格加行级免费/全额优惠。实际 HTTP 验证120元商品全额优惠后为0，加20运费后为未付款20，预付款和实收均0。
   - 普通手动零单价仍拒绝且数据不变；Vue 实际脚本测试验证已关联样品的原零价例外不扩展到普通订单。

### 实际本机 HTTP 与数据库

通过本地应用创建合成订单10–13；订单9为请求格式调试时创建的隔离夹具，不是真实订单。所有写入均在隔离数据库。

- 订单10：已付120加运费20 → 预付款120/应收140；回读后再次保存仍120/140，不补流水。证据 `http-paid-fee-first.json`、`http-paid-fee-repeat.json`。
- 订单11：30/100同时加运费20和结清 → 409指导分两次保存，整个业务快照与审计不变；分开保存 → 已付120、原预付款30、无补造实收。证据 `http-mixed-rejection.json`、`http-split-settlement.json`。
- 订单12：正价120全额优惠 → 零应收，加20运费 → 未付20；直接零手动价仍400且无变更。证据 `http-legal-zero-fee.json`、`http-ordinary-zero-rejected.json`。
- 订单13：累计凭证实收100，省略运费协议减到99 → 400“超出应收”；确认实际运费后，同一请求 → 400“已确认实际费用”，订单、明细、快照、审计完全不变。证据 `http-no-protocol-rejected.json`、`http-frozen-rejected.json`。
- 订单13：独立 `PUT /api/mini/employee/orders/13/status` 在冻结后仍成功，原预付款30、累计实收100、原凭证保留，商品与运费快照不变。证据 `http-frozen-independent-status.json`。
- 脚本初次请求把表单字符串状态ID传入整单API、把字符串金额传入状态API，分别被类型校验拒绝；按各API类型修正后继续。不是产品失败，最后一项单独续跑，没有重复整个套件。脚本位于任务 `runtime/followup_http.py`、`followup_http_status.py`。
