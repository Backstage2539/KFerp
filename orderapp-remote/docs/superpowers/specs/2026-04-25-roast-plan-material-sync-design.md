# 生产计划烘焙建议与物料需求汇总联动设计

## 背景

当前 `生产计划/开始生产` 页面里，`烘焙建议` 与 `物料需求汇总` 使用了两套不同口径：

1. `烘焙建议` 按设备最小/最大烘焙量，给出每种商品的建议烘焙批次。
2. `物料需求汇总` 仍然直接按 `gap_g / 出品率` 估算原料需求。

这会导致两类问题：

- 对拼配商品，`物料需求汇总` 没有按最终建议投料数和 BOM 配比计算，结果明显偏小。
- `烘焙建议` 即使被人工调整，也不会同步影响 `物料需求汇总` 与后续开始生产的 `投料数`。

## 目标

建立统一口径：

- `烘焙建议` 的 **每锅数量** 可编辑。
- `锅数 × 每锅数量` 作为该商品的 **最终投料数**。
- `物料需求汇总` 基于最终投料数和商品 BOM 配比计算。
- `开始生产` 默认使用该最终投料数作为 `input_g`。

## 范围

包含：

- `生产计划/开始生产` 页面迁移到统一的 Vue/Vite 前端架构
- `烘焙建议` 支持编辑每锅数量
- 新增最终投料数展示
- `物料需求汇总` 改为按最终投料数 + BOM 计算
- 修改烘焙建议后，页面内同步刷新物料需求汇总与投料数
- 开始生产提交时，按联动后的最终投料数提交 `input_g`

不包含：

- 新增独立数据库表保存烘焙建议草稿
- 调整设备排锅算法
- 修改 BOM 配方结构
- 生产中页面逻辑调整

## 已确认业务口径

1. 可修改的是 `每锅数量`，不是总量。
2. 一个商品内每种生豆的 BOM 配比固定。
3. 该商品最终投料数 = `每锅数量 × 锅数`。
4. `物料需求汇总` 对生豆类物料，按最终投料数乘 BOM 比例计算。
5. 如果修改了 `每锅数量`，`物料需求汇总` 必须同步变化。
6. 开始生产时，最终提交的 `投料数(input_g)` 应取烘焙建议联动后的最终投料数。

## 方案选择

采用“后端统一口径 + 前端即时联动”的方案：

- 后端在生成页面时输出每个计划商品的默认烘焙建议和 BOM 拆分数据。
- 前端在统一的 Vue/Vite 页面内根据用户修改的 `每锅数量` 做即时重算与展示。
- 点击 `开始生产` 时，把联动后的最终投料数写回表单提交给后端。
- 后端继续以提交上来的 `input_g` 为最终权威值，写入运行项。

这样可以保证：

- 页面展示与提交口径一致
- 不需要额外增加烘焙建议持久化模型
- 改动范围集中在 `生产计划/开始生产` 页面及其计算函数

## 数据设计

### 1. 生产计划展示数据扩展

现有生产计划接口返回的数据需要增加面向页面联动的数据：

- 每个计划商品的默认烘焙建议
- 每个商品对应的 BOM 物料拆分
- 每个商品默认最终投料数

建议新增两个展示结构：

- `RoastPlanRow`
  - `ProductID`
  - `ProductName`
  - `Machine`
  - `BatchCount`
  - `DefaultBatchG`
  - `FinalInputG`
  - `YieldRate`

- `RoastPlanMaterialRatio`
  - `ProductID`
  - `MaterialName`
  - `MaterialUnit`
  - `RatioPct`

说明：

- `RoastPlanRow` 用于 Vue 页面渲染与前端联动。
- `RoastPlanMaterialRatio` 用于前端根据最终投料数重算物料需求。
- 这两个结构只服务当前页面，不新增数据库表。

### 2. 开始生产提交数据

现有 `startProduction()` 会提交每个商品的 `input_g`。

本次不新增新的后端提交接口，只调整提交值来源：

- 页面初始化时：`input_g = 默认最终投料数`
- 用户改 `每锅数量` 后：同步更新对应商品的 `input_g`
- 表单提交时：后端直接使用该联动后的 `input_g`

## 页面与交互

### 1. 生产计划（缺口 > 0）

保留当前表格，但 `投料数(g)` 的默认值不再单纯等于 `ceil(gap_g / yield)`，而是优先采用 `烘焙建议` 联动后的最终投料数：

- 若该商品存在烘焙建议：
  - `投料数(g) = 每锅数量 × 锅数`
- 若无烘焙建议：
  - 退回当前逻辑：`ceil(gap_g / yield_rate)`

### 2. 物料需求汇总（预计消耗）

重算口径改为：

- 生豆 / 原豆类 BOM 物料：
  - `need = ceil(final_input_g × ratio_pct / 100)`
- 非重量类 BOM 物料：
  - 仍按当前包装逻辑计算，不使用烘焙投料数替代件数逻辑
- 规格袋等包材：
  - 继续按缺口件数/规格计算

这意味着：

- 生豆类汇总跟随烘焙建议
- 包材类汇总继续跟随成品缺口

### 3. 烘焙建议

当前表格：

- 物料
- 推荐机器
- 烘焙建议(kg/锅)
- 锅数
- 熟豆总需求(kg)
- 损耗比

调整为：

- 物料/商品
- 推荐机器
- `每锅数量(g)` 可编辑
- 锅数
- `最终投料数(g)` 只读展示
- 熟豆总需求(kg)
- 损耗比

说明：

- 继续保留 `锅数` 为只读，由现有设备拆锅逻辑给出。
- 用户只改 `每锅数量(g)`。
- 前端在输入变化时重算 `最终投料数(g)`。

## 核心计算规则

### 1. 默认烘焙建议

现有拆锅逻辑继续使用：

- 默认总投料数由设备排锅函数给出
- 默认每锅数量 = 拆锅结果中的单锅克数
- 锅数 = 拆锅结果长度

例如：

- 默认拆锅结果为 `[2000]`
- 则：
  - 每锅数量 = `2000`
  - 锅数 = `1`
  - 最终投料数 = `2000`

### 2. 用户修改后联动

对任一商品：

- `final_input_g = batch_g × batch_count`
- 生产计划表内 `input_g = final_input_g`

### 3. 生豆物料需求

若商品 BOM 中有两个生豆：

- A：70%
- B：30%

且该商品最终投料数为 `2000g`

则物料需求汇总应为：

- A：`1400g`
- B：`600g`

两个生豆合计必须回到 `2000g`。

## 后端改动点

- 生产计划相关 handler / API
  - 生成可编辑烘焙建议展示结构
  - 返回 Vue 页面联动所需的 JSON 数据
  - 默认 `PlanRows.InputG` 改为优先取烘焙建议最终投料数
- `roast_split.go`
  - 继续负责设备拆锅，但要把批次数与默认单锅克数暴露给页面
- `produce_materials_bom.go`
  - 新增基于 `final_input_g` 计算 BOM 生豆需求的函数
  - 保留包材按缺口件数计算

## 前端改动点

- `生产计划/开始生产` 已迁移到统一的 Vue/Vite 前端，旧 `templates/unprod_summary.html` 不再保留
- Vue 页面补齐：
  - `烘焙建议` 可编辑 `每锅数量(g)` 输入框
  - `最终投料数(g)` 展示列
  - 页面内联动状态管理：
    - 修改每锅数量时，更新最终投料数
    - 更新对应计划表的 `投料数(g)`
    - 重算并刷新 `物料需求汇总`
- 不再继续在 HTML 模板页上增加该功能

## 回退与兼容

- 对没有 BOM 的普通商品，继续沿用现有兜底逻辑：
  - 生豆名按 `<商品名> 生豆`
  - 数量按最终投料数估算
- 对没有烘焙建议的商品：
  - `input_g` 退回原默认值
  - `物料需求汇总` 退回现有缺口/出品率逻辑

## 测试与验收

### 单元测试

- 默认烘焙建议能生成 `每锅数量 / 锅数 / 最终投料数`
- 修改每锅数量后，商品最终投料数更新正确
- 生豆 BOM 汇总按最终投料数计算，而不是按 `gap_g`
- 包材汇总仍按件数逻辑计算

### API / 页面验证

- `GET /produce/unproduced?...&plan=1` 返回页面包含：
  - `每锅数量(g)`
  - `最终投料数(g)`
  - 联动脚本所需数据
- 修改每锅数量后，再点击开始生产：
  - 对应 `input_g` 应为修改后的最终投料数
- 物料需求汇总应随修改即时变化

### 关键验收样例

以“曲奇拼配”为例：

- 缺口：`1000g`
- 设备建议：`1锅 × 2000g`
- BOM：
  - 豆子 A：70%
  - 豆子 B：30%

则页面应表现为：

- 烘焙建议最终投料数：`2000g`
- 生产计划投料数：`2000g`
- 物料需求汇总：
  - 豆子 A：`1400g`
  - 豆子 B：`600g`

若用户把每锅数量从 `2000g` 改成 `2500g`：

- 最终投料数变为 `2500g`
- 生产计划投料数变为 `2500g`
- 物料需求汇总同步变为：
  - 豆子 A：`1750g`
  - 豆子 B：`750g`
